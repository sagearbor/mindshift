# `scripts/live_e2e.py` — the phone-shaped end-to-end client (2026-08-24)

> One command that ACTS AS THE PHONE and walks the whole realtime + analysis
> path of a running MindShift server: Firebase auth → voiceprint enrollment
> → the live WebSocket (config, PCM streaming, `turn_local` per turn, cloud
> suggestions + partial previews, tone flags, identity verdicts, `stop` →
> `session_complete.latency_summary`) → `POST /sessions/live` → batch
> analysis → reflection → detail/growth → share → the therapist's
> `GET /sessions`. Prints a compact ✅/⚠️/❌ report and exits non-zero on
> any ❌. The same code runs in-process in CI
> (`server/tests/test_live_e2e_inprocess.py`), so it cannot rot.

## Why

The three realtime tracks (#129–#140) each have unit/endpoint coverage, but
nothing exercised the seams *between* them the way the phone does — token in
the config frame, audio + `turn_local` on one timeline, enrichment recovered
from the ring buffer, the episode built from the phone's own turns, the
therapist seeing it through a share. This script is that walk, against
production or a local server, with the scene pack (Foundation D) as the
"phone's" ground truth.

## Usage

```bash
# throwaway accounts (Firebase email/password sign-up, +addressed on one inbox)
python scripts/live_e2e.py --base-url https://<cloud-run-url> --signup \
    --signup-email-base sagearbor@gmail.com --scene scene_couple_escalation

# existing accounts (Identity Toolkit signInWithPassword, public web API key)
python scripts/live_e2e.py --base-url https://... \
    --email you@example.com --password ... \
    --therapist-email doc@example.com --therapist-password ... \
    --scene scene_family3 --speed 2

# tokens you already hold
python scripts/live_e2e.py --base-url http://localhost:8000 \
    --id-token <patient token> --therapist-id-token <therapist token>
```

| Flag | Meaning |
|---|---|
| `--scene` | `scene_couple_escalation` (default), `scene_family3`, `scene_meeting4` — any `server/tests/fixtures/audio/test_recording_scene_*` pair |
| `--speed N` | stream N× faster than real time. Turn timestamps are on the AUDIO timeline so they stay exact; but the server's latest-wins queue will supersede pending turns when the LLM can't keep up, so use 1 (default) when you want every turn coached |
| `--mode` | `earpiece` (default) / `speaker` / `therapist` — the live session's mode |
| `--no-enroll` | skip `POST /voice/enroll-direct`. With enrollment on (default) the server has a voiceprint and emits a `speaker_identity` verdict per turn |
| `--analysis-timeout` | seconds to poll `GET /recordings/{id}` for the batch analysis (default 180) |
| `--cleanup` | delete the episode + voiceprint, and (for `--signup`) the throwaway Firebase accounts, at the end |
| `--json` | also print the raw report dict |

Requirements: the repo venv (`httpx`, `websockets`, `numpy` — all in
`requirements.txt`); network access to the server and, unless you pass
tokens, to `identitytoolkit.googleapis.com`. The Firebase web API key is
the app's PUBLIC client key from `apps/mobile/src/auth/firebaseConfig.ts`
(override with `EXPO_PUBLIC_FIREBASE_API_KEY` / `--firebase-api-key`).

## What the "phone" sends

* **Config frame** (first frame, carries auth): `{"type":"config",
  "id_token": …, "empathy_slider": 60, "interject_level": 0,
  "self_speaker": <scene self label>, "tts": "on-device",
  "report_latency": true}` — the same shape `useAudioStream.ts` sends when
  the on-device loop is active.
* **Audio**: the scene WAV (16 kHz mono int16) as 3200-byte binary frames
  (100 ms) on a real-time clock (`--speed` scales it).
* **`turn_local`** per scene turn, released once that turn's audio (+ a
  0.3 s simulated on-device STT lag) has been streamed — so the server's
  ring buffer already holds the slice, as on a real phone. Fields exactly
  as `fastLoop.ts` builds them:
  * `speaker` / `text` / `start_time` / `end_time` from the scene meta
    (timeline reconstructed like `test_diarize_regression_ladder._build_turns`);
  * `is_self` from the meta's `self_speaker`; the phone is an oracle here
    (`speaker_person_id: "self"`, `speaker_match_score: 0.9` for self;
    null for everyone else);
  * `prosody` measured with `server/prosody.py` on the same samples the
    phone's port (`apps/mobile/src/live/prosody.ts`) measures:
    `rms_dbfs`, `pitch_hz` (null when unvoiced), `speech_rate`
    (words/second);
  * `text_tone` from the EMOTION → TEXT-TONE table below;
  * `suggestion: null`, `suggestion_source: null`, `tts_source: "on-device"`.
* **`stop`** after the last turn; then it waits for `session_complete`.

### EMOTION → TEXT-TONE table

The phone's on-device text-tone model scores each turn 0–100 on warmth /
defensiveness / sarcasm / sadness / frustration plus a free label. The
client has no model, so it derives those from the scene's
`scripted_emotion` (fine table) with `emotion_coarse` as the fallback, and
the table is pinned to `server/live_sessions.py`'s reading rules
(`is_escalated`: label `angry` OR frustration/defensiveness/sarcasm ≥ 60;
`tone_label`: dominant dimension, warmth ≥ 60 → "warm"). A test asserts
every angry scripted emotion reads as an escalation and nothing else does.

| scripted_emotion | warmth | defens. | sarcasm | sadness | frustr. | label |
|---|---|---|---|---|---|---|
| tense_rising | 25 | 55 | 10 | 5 | 65 | angry |
| defensive_rising | 20 | 80 | 15 | 5 | 70 | angry |
| shout_angry | 5 | 70 | 20 | 5 | 95 | angry |
| cold_contempt | 0 | 60 | 75 | 10 | 85 | angry |
| hurt_sad | 45 | 20 | 0 | 85 | 20 | sad |
| sullen_sad | 30 | 35 | 5 | 75 | 30 | sad |
| scared_shaky | 40 | 25 | 0 | 70 | 15 | sad |
| warm_happy | 90 | 0 | 0 | 0 | 0 | warm |
| calm_open | 60 | 10 | 0 | 5 | 5 | neutral |
| calm_guarded | 40 | 35 | 5 | 10 | 20 | neutral |
| calm_neutral | 50 | 15 | 5 | 5 | 10 | neutral |
| calm_close | 65 | 5 | 0 | 5 | 5 | neutral |
| calm_deescalate | 60 | 10 | 0 | 5 | 15 | neutral |
| repair_apology | 70 | 5 | 0 | 25 | 5 | neutral |

Fallback by `emotion_coarse`: angry → (15, 65, 15, 5, 80, "angry"),
sad → (40, 25, 0, 80, 20, "sad"), happy → (90, 0, 0, 0, 0, "warm"),
neutral → (50, 15, 5, 5, 10, "neutral").

## The report

One line per stage; ⚠️ is informational (an optional server capability
that isn't deployed / a soft model metric), ❌ is a broken path and fails
the run.

| Line | ✅ when | ❌ when | ⚠️ when |
|---|---|---|---|
| voice enrollment | `POST /voice/enroll-direct` 200 | any other non-503 answer | 503 (speaker-ID deps not on the server) or `--no-enroll` |
| live ws | `config_ack`, every frame + `turn_local` sent, `session_complete`, close 1000 | anything else (`auth_error`, no completion in 60 s, connection error) | — |
| latency_summary | present on `session_complete` (per-stage p50/p95/n printed below the checks) | missing | — |
| cloud suggestions | ≥1 final `suggestion`, all `suggestion_source: "cloud"`, 0 `suggestion_error`; prints counts by kind (response/nudge), partial previews, time-to-first-partial p50/min/max measured client-side from `turn_local` send | no final suggestion, or any `suggestion_error` whose reason is NOT `llm_parse_error` (provider auth/timeout/crash) | only `llm_parse_error` errors (the model occasionally answers with unparseable JSON — the path works; reasons + counts printed) |
| server transcripts | 0 `transcript` events (nothing coached twice) | — | ≥1: the server's own transcriber (Deepgram) finalized spans BEFORE the phone's `turn_local` for them arrived, so overlap suppression could not drop them and they were coached twice — counted so the owner can see it |
| identity verdicts | every `speaker_identity` agrees with the scene's `self_speaker` | enrolled but no verdict arrived | not enrolled; or some verdicts disagree (soft — the scores are printed) |
| tone flags | any `tone_flag` | — | none (production default `MINDSHIFT_TONE_AUDIO=dark`) |
| episode ingest | `POST /sessions/live` 201 with `self_speaker` = the scene's | otherwise | — |
| batch analysis | `analysis_status` reaches `full` within the bound | `failed` (error printed) or timeout | not scheduled (too few turns) |
| reflection | `POST /episodes/{id}/reflect` 200 with ≥1 reflection | otherwise | — |
| episode detail | self labelled "You"; `tone_summary.self.escalation_turns` == the scene's angry self turns | otherwise | — |
| growth | `/growth` has a point for the episode | otherwise | — |
| share | `POST /recordings/{id}/shares` 200 | otherwise | — |
| therapist visibility | therapist's `GET /sessions` lists it with `shared: true`, ≥1 `couldHaveSaid`, the same escalation turns | otherwise | — |
| therapist detail read | therapist's `GET /recordings/{id}` 200 `shared: true` | otherwise | — |

## In-process CI run (`server/tests/test_live_e2e_inprocess.py`)

`live_e2e.run_e2e` — the exact function the CLI calls — runs against a real
uvicorn on `127.0.0.1` serving `main.app` (real WebSocket + HTTP over the
loopback, lifespan off), for `scene_couple_escalation` and `scene_family3`
at 25× speed, asserting the report has no ❌ plus the numbers that prove the
whole protocol ran (a `turn_local` per turn, streamed partial previews, an
identity verdict and a tone flag per turn, the scene's escalation turns
in both the owner's detail and the therapist's row, the growth score).

Providers are replaced at the existing DI seams only:
`app.state.{transcriber_factory,tts_client,llm_client,recordings_store}`
(a routing LLM double with a real `stream_complete`, an in-memory store
with the share + voiceprint surface) and the `audio_pipeline.tone_id` /
`audio_pipeline.speaker_id` module attributes (label-echo doubles — the
real ECAPA behaviour on these scenes is pinned by `test_diarize_scenes.py`
and exercised by the production run). Auth is the suite's existing keyless
harness: the WS handshake presents conftest's fake token (`tok-user-a` →
`user-a`), REST sends the `X-Test-Uid` override — the client code is
identical, only the `Account` it is handed differs.

## Benchmarking the cloud-suggestion path (`scripts/bench_suggestions.py`)

The numbers this script reports for production (`latency_summary`,
time-to-first-partial) can be reproduced against the real Anthropic API
without a deploy:

```bash
# the LLM stage alone, per prompt/request variant (legacy vs lean, cache
# marker, structured outputs), p50/p95 + parse failures + cache usage
python scripts/bench_suggestions.py --n 20 --nudges

# the whole realtime pipeline in-process (uvicorn + real LLM, null
# transcriber/TTS, keyless auth) driven by this file's phone-shaped client;
# --legacy flips every perf knob back to the pre-perf/cloud-suggestion-latency behaviour
python scripts/bench_suggestions.py --mode ws --scene scene_couple_escalation,scene_family3 --speed 2 --repeat 3
python scripts/bench_suggestions.py --mode ws --legacy ...
```

The perf knobs (all env-overridable, read once at import):
`MINDSHIFT_LIVE_PROMPT`, `MINDSHIFT_SUGGESTION_MAX_TOKENS`,
`MINDSHIFT_NUDGE_MAX_TOKENS`, `MINDSHIFT_PARSE_REPAIR`,
`MINDSHIFT_LOCAL_FIRST_CONCURRENCY` (audio_pipeline.py) and
`MINDSHIFT_PROMPT_CACHE` (llm_client.py — off by default; see the comment
there for the measurement).

## Known limits

* The phone here is an oracle for speaker labels/`is_self` (from the scene
  meta); it does not run the on-device ECAPA/VAD/STT. Those are covered by
  the mobile Jest suites and real-hardware verification (see the realtime
  handoff doc §6).
* `--speed > 1` shortens the wall clock but the server's latest-wins
  suggestion queue then supersedes turns the LLM couldn't reach in time —
  fewer suggestions is expected, not a failure.
* Identity verdicts against production depend on `speaker_id` deps being
  present on the server (enrollment 503s honestly otherwise → ⚠️).
